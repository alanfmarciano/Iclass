# Arquitetura — IClass V3

Documento para quem mantém o projeto. Explica as camadas, o fluxo de dados e as decisões estruturais. Escrito para ser compreensível inclusive por dev júnior.

## 1. Visão macro

```
Navegador (React SPA)  ──HTTP /api──►  Express (Node)  ──►  SQLite (arquivo)
   web/                                   backend/            data/database.db
```

- **Frontend** (`web/`): apenas apresentação e chamadas de API. Não decide regra de negócio.
- **Backend** (`backend/`): **fonte de verdade** (server-authoritative). Autenticação, liberação de conteúdo, correção de prova e sanitização de gabarito ficam aqui.
- **Local-first**: tudo roda na máquina do professor; alunos acessam pela rede local. O mesmo processo Express serve a API e o build estático do React (`web/dist`).
- **Pacote de release** (fase 3, A15): `scripts/release/montar-pacote.js` monta o ZIP do Windows com `backend/`, `web/dist/`, as dependências de produção, o binário do sqlite3 e o Node portátil, sem `web/src`. O servidor sabe em que modo está pelo `buildIntegrity.buildMode()` (`desenvolvimento` com `web/src`, `pacote` com o `release-manifest.json`) e, no pacote, confere o `web/dist` pelo SHA-256 do manifesto no boot. Detalhes em OPERACAO_SEGURANCA_TESTES.md.

## 2. Camadas do backend

```
backend/
├── server.js          # bootstrap: CORS, static, monta routers, error handler, listen
├── runtimePaths.js    # resolve DATA_DIR, CONTENT_DIR, ARCHIVE_DIR (variável de ambiente > iclass-pastas.json do pacote > padrão)
├── database.js        # SQLite key-value + espelho em memória (db.memory) + db.save() + registro COLLECTION_TABLES
├── middlewares.js     # validateAdmin, validateStudentSession, sanitização, RBAC
├── routes/            # um router por área funcional
└── utils/             # regras isoladas e reutilizáveis (backup, provas, segurança, etc.)
```

### server.js — ordem de montagem (importa)

1. `assignRequestId` (X-Request-Id), `cors`, cabeçalhos de segurança (`utils/securityHeaders.js`: CSP, `nosniff`, `X-Frame-Options`, `Referrer-Policy`; sem `X-Powered-By`; ver SEGURANCA.md), cabeçalho do build, `Cache-Control: no-store` em todo `/api` (e em `.html`/`.js` fora de `/assets`, como `/data.js`), `compressTextResponses` (gzip das respostas de texto acima de 1 KB, `utils/httpCompression.js`; fica antes de quem espera o COMMIT para responder) e leitor JSON com limite por sessão (10 MB com sessão de instrutor, 512 KB nos demais, inclusive o lote de teclas da prova, que o cliente manda em lotes de até 500 desde o H2-C), seguido de `req.body = {}` quando não há corpo. O leitor de query fica com o último valor de parâmetro repetido. Depois, `createPersistenceContext` (H1-a: a resposta só sai depois do COMMIT; gravação que falhou vira 503 `retryable`) e `createNetworkPolicy` (H6b/H6c, `utils/networkPolicy.js`: `settings.network.adminAccess` decide se outro aparelho abre o painel do professor; em `'rede'` o pedido http de outro aparelho para o painel é redirecionado para https e a API responde 403 `https-required`, em `'local'` 403 `local-only`; o aviso de painel sem proteção sai em `/api/connection`), antes de `/assets`, dos arquivos e de qualquer rota de professor.
2. `/assets` → `serveBuildAssets` (`utils/staticAssets.js`): terminal, com cache imutável de um ano e as versões `.br`/`.gz` do build; nome que não existe é 404 com no-store, nunca o `index.html`. A regra de nomes (`isServableAssetName`: letras sem acento, números, `.`, `_` e `-`, sem ponto no começo nem no fim) é a mesma que o build usa para dar nome aos arquivos (`toServableAssetName` no `sanitizeFileName` do `vite.config.js`) e que o `check:bundle` confere em cada arquivo de `web/dist/assets`. Por isso o `staticAssets.js` entra no hash do build (`BACKEND_BUILD_FILES` em `utils/buildIntegrity.js`): mudar a regra deixa o build desatualizado e o servidor pede `npm run build`.
3. Rotas de arquivos controlados: `/uploads/:filename`, `/imagens/:filename` (passam por `sendControlledFile`).
4. `express.static(web/dist, { index: false })` — o resto da raiz do build, sem entregar o `index.html` sozinho.
5. Guard de RBAC do admin em `/api/admin` (`adminRbacGuard`).
6. `previewSessionGuard` (fase 3, P5-S6a, `utils/previewAccess.js`): pedido com `x-preview-session` (pré-visualização como aluno) fora de `/api/admin` só passa nas rotas de leitura de `PREVIEW_READ_ROUTES`; as outras respondem 403 `preview_read_only`. Fica antes de `proctoring` porque `log-activity` grava.
7. Routers montados: `proctoring`, `testmode`, `setupMode`, `common`, `student`, `admin` (dentro dele, depois de `createAdminCoursesRouter`, o `createAdminPreviewRouter` de `adminPreview.js`).
8. Fallback do app: qualquer outro caminho (inclusive `/`) recebe o `index.html` com no-store; `/assets` nunca chega aqui.
9. `errorHandler` no fim.

### Boot do servidor — ordem (`prepareServer`, fase 2, H3b)

`startServer` (fase 2, H3c) instala os tratadores do processo, confere o build, abre a porta com o handler de boot e só então chama `prepareServer()` (os testes usam o mesmo `prepareServer`, sem o build e sem `listen`; ver "Processo, supervisor e códigos de saída" abaixo). A fase do boot (`loading`, `restoring`, `checking`) aparece no `/api/health`:

1. `db.init()`: carga, migrações e a sincronização das turmas com as aplicações, que só grava quando alguma turma mudou de fato (o boot não regrava turmas, alunos nem presenças nem diz "Provas online resetadas" sem motivo).
2. `serverLifecycle.loadPreviousRun()`: lê `DATA_DIR/runtime/heartbeat.json` da execução anterior (quando parou, se foi parada limpa). A retomada das sessões (passo 3) usa o mesmo dado (`previousRun().downtimeMs`). Heartbeat de menos de 15 s de outro processo ainda vivo (um segundo servidor aberto na mesma pasta, com o primeiro no ar) não é queda: este processo não devolve tempo nem grava o seu heartbeat.
3. Retomada das sessões (H3a-2, `restoreSessions` de `utils/authSessions.js` com as linhas de `auth_sessions` que o `db.init()` leu): com até 60 min fora do ar, aluno e professor seguem com o mesmo token (só de conta que ainda pode entrar: aluno cadastrado e ativo, instrutor cadastrado); com mais, ou sem heartbeat, todos entram de novo. As que não voltaram saem da tabela já aqui (uma gravação), menos num segundo servidor com o primeiro ainda no ar. Depois, migração do fórum e varredura da lixeira. `prepareServer()` devolve `{ outage, sessions }` (o resumo da retomada).
4. `compensateBootOutage`: o tempo do último heartbeat até agora volta para as provas em andamento como pausa `server_outage` (até 15 min; acima disso só o registro em `application.outages` e na auditoria da prova) e é gravado. Aplicação em que ninguém tinha mais tempo quando o servidor parou (todos entregaram, cronômetro por tentativa sem ninguém fazendo, prazo coletivo já vencido) fica sem pausa, sem registro e sem auditoria.
5. Primeira varredura do fim do tempo (`settleExpiredAttempts`), depois da devolução: quem teve o prazo vencido com o servidor fora não é entregue no boot. Repete a cada 10 s.
6. `startHeartbeat`: grava o heartbeat a cada 5 s e liga a verificação de tempo parado (`detectGap`: mais de 30 s sem verificação com o processo vivo, como notebook suspenso, vira queda `suspended`), que roda também antes de toda conta de prazo (`computeAttemptDeadline`).
7. Backup automático (fora do `TEST_MODE`) e os timers (`registerTimer`). Depois, no `startServer`: `createApp()`, a troca do handler de boot pelo app, `markReady` e o banner "iniciado com sucesso".

O fim do desligamento ordenado grava o heartbeat com `clean: true` e o motivo (`markCleanShutdown`): o próximo boot registra reinício, não queda (o motivo `fatal` conta como queda). Processo morto à força (kill -9, `taskkill /f`, falta de energia) conta como queda. O ouvinte de `exit` do `serverLifecycle` continua como rede de segurança para a saída com código 0 fora do desligamento ordenado.

### Processo, supervisor e códigos de saída (fase 2, H3c)

**Ordem do `startServer`:**
1. `installProcessHandlers`: `uncaughtException` (grava no `crash.log` pelo `logError`, marca "com problemas" e, sob o supervisor, faz o desligamento com motivo `fatal`, menos depois de 3 quedas em 10 min; sem supervisor o processo continua com aviso), `unhandledRejection` (só o registro), SIGINT/SIGTERM/SIGHUP/SIGBREAK e a mensagem `{ type: 'shutdown' }` do supervisor, todos para o mesmo `serverLifecycle.requestShutdown`.
2. `verifyBuild` (build ausente ou desatualizado: sai com 2, dizendo que é o build).
3. Conexão segura (H6c, `utils/secureConnection.js`): `secureConnection.prepare` lê ou cria em `DATA_DIR/tls` a CA própria do IClass e o certificado do servidor com os IPs da máquina (`networkAddresses`), antes de abrir a porta, para o https valer já no "iniciando". Se não der (pasta sem permissão, arquivo no lugar da pasta), o console mostra só a linha em português (o detalhe vai para o `crash.log`) e o servidor sobe só em http: o https nunca impede o boot. CA refeita nesta leitura (danificada ou pasta `tls` que sumiu): aviso no console de que os aparelhos precisam instalar o certificado de novo.
4. `createDualServer` (`utils/dualListener.js`): http e https na **mesma porta**, decididos pelo primeiro byte de cada conexão (0x16 = handshake TLS), os dois com o mesmo **handler trocável** (`createSwitchableHandler`), que começa no app de boot (`createBootApp`: `/assets` pelo mesmo `serveBuildAssets`, `GET /api/health` 503 `starting` com a fase, todo `/api` 503 `{ starting: true }` com `Retry-After: 3`, o resto uma página "iniciando"). Porta ocupada ou sem permissão: sai com 2, sem tocar no banco (`listenWithRetry` tenta mais 5 vezes, 1 s entre elas, só logo depois de um reinício).
5. `writeControlToken` (`runtime/control.token`) e `prepareServer()`. Falha do banco: código 3 para banco danificado (`ICLASS_DB_CORRUPT`, `SQLITE_CORRUPT`, `SQLITE_NOTADB`, com a mensagem que cita o `backup-cli.js`), 1 para as outras (arquivo que não abre, disco). Toda falha de boot apaga o `control.token` antes de sair.
6. `reconcileSecureConnectionCa`, já com os dados carregados: compara a impressão digital da CA com `settings.network.caFingerprint` (a restauração mantém o `settings.network` de agora e o backup nunca leva `data/tls`). Na primeira vez de verdade só grava; se a pasta `tls` sumiu inteira e a CA agora é outra, grava `tls/ca-recriada.json` e avisa no console e em Sistema → Rede.
7. `createApp()`, `handler.set(app)`, `markReady` (com as sessões retomadas), banner, o vigia da rede (`startNetworkWatcher`: a cada 30 s confere o endereço recomendado; com IP novo refaz o certificado do servidor e troca a quente por `updateTls`, sem reiniciar nem instalar nada de novo nos aparelhos) e `{ type: 'ready' }` para o supervisor.

Cada falha do boot sai por `describeBootFailure`, que diz a causa certa (build, porta, banco) e grava no `crash.log` com a etapa (`build`, `listen`, `database`, `boot`).

**Códigos de saída** (`serverLifecycle.EXIT_CODES`): 0 parada normal; 1 erro em execução ou falha passageira ao abrir o banco (o supervisor religa); 2 configuração, porta ocupada ou build ausente (não religa); 3 banco danificado (não religa); 75 reinício pedido (o supervisor religa na hora).

**Desligamento ordenado** (`requestShutdown({ restart, reason })`, um só por processo; chamado de novo devolve a mesma promessa): limpa todos os timers registrados (todo `setInterval` do servidor passa por `serverLifecycle.registerTimer(nome, handle)`, com `unref()`; um teste confere isso no código), fecha a porta (as conexões paradas na hora, as outras em até 2 s), `db.close()` (grava e aplica o `-wal`; no motivo `fatal`, no máximo 5 s), `markCleanShutdown`, apaga o `control.token` e sai (75 no reinício sob o supervisor, 1 no `fatal`, 0 no resto). Passando de 10 s, sai com 1 assim mesmo. Pedido ainda no boot (sinal, rota de controle, supervisor) sai sem gravar (a memória pode não estar carregada) e sem marcar parada limpa: o heartbeat para antes da saída, e o próximo boot conta o tempo fora do ar pelo último heartbeat gravado; o código de saída é o do pedido (0, 75 ou 1). No Reiniciar sem supervisor, relança o servidor antes de sair (Windows: `cmd.exe` com `ping` de espera, como antes; outros sistemas: `node backend/server.js` destacado, com a saída em `logs/servidor.log`).

**Supervisor** (`backend/supervisor.js`, `npm run start:supervised`): sobe `backend/server.js` com `fork` e `ICLASS_SUPERVISED=1` (mais o número de reinícios, o último código e as quedas recentes, que o cartão Saúde mostra), copia a saída para o console e para `DATA_DIR/logs/servidor.log` (com data e hora, sem as sequências do terminal, girando aos 5 MB com 3 anteriores) e decide depois de cada saída (`decideAfterExit`): 0 para; 75 religa na hora; 2 e 3 param sem laço; outro código ou sinal religa com espera de 1, 2, 5, 10 e 30 s (a espera zera depois de 5 min pronto); 5 falhas seguidas antes de ficar pronto: para com 1. Com SIGINT/SIGTERM/SIGHUP/SIGBREAK, manda `{ type: 'shutdown' }` ao servidor, espera até 15 s (depois SIGKILL) e sai com o código dele, nunca religando enquanto para. Grava `runtime/supervisor.pid`. Se o supervisor morrer sozinho (kill -9, "Finalizar tarefa" no `node.exe` dele, `taskkill` sem `/T`), o canal IPC fecha e o servidor faz o desligamento ordenado (`disconnect`), apagando o `supervisor.pid` velho: não fica servidor órfão segurando a porta.

**Launcher** (fase 3, A16 / P6-S4; contratos C6 e C11): `backend/scripts/launcher.js` é o menu do professor (readline) e os subcomandos (`iniciar`, `parar`, `reiniciar`, `backup`, `restaurar`, `senha`, `endereco`, `status`, `demonstracao`, `parar-demonstracao`); no pacote, o `IClass.cmd` (raiz do pacote, ASCII com CRLF, modelo em `scripts/release/modelos/`) chama esse arquivo com o Node do pacote. As ações ficam em `backend/utils/launcherCore.js` (`createLauncher`, com spawn, HTTP, relógio e perguntas injetáveis para os testes; não carrega o banco). Ligar abre o supervisor numa janela própria (Windows: `cmd.exe /d /s /c start "IClass" [/min] "node" "supervisor.js"`, com o título vindo de `ICLASS_JANELA_TITULO`; outros sistemas: processo destacado) e espera o `/api/health` com a instância de `runtime/servidor.json`, mostrando as fases do boot (90 s; 10 min nas fases de atualização). Desligar é pela rota de controle (`POST /api/system/control`, token de `runtime/control.token`); sem resposta em 15 s, `taskkill /T` sem `/f` na árvore do supervisor (só se o PID ainda é de um `node.exe`; no Linux, pelo `/proc/<pid>/exe`, e o supervisor só troca o `process.title` no Windows), e o encerramento forçado só com a pessoa confirmando. Antes de desligar, reiniciar, fazer backup ou restaurar, o launcher pergunta ao `GET /api/system/control/status` pelas provas em andamento e pelos alunos conectados. A porta vem do `servidor.json` ou do `PORT`/`--porta`: nada de `netstat` nem porta fixa. A demonstração é outra instância do mesmo servidor na porta 3100, com `TEST_MODE` e pastas próprias recriadas a cada vez (marca `.iclass-demonstracao`), nunca dentro da pasta de dados de verdade.

**Instalação, atualização e volta de versão** (fase 3, A17 / P6-S5; D10, D13 e D24 do P6): `backend/utils/launcherInstall.js` (`createInstallActions`, montado e exposto pelo `createLauncher` com as mesmas injeções) faz `instalar`/`atualizar` (do pacote descompactado: confere o `release-manifest.json` e o SHA-256 de cada arquivo, copia para `<raiz>\programa\<versão>` por `programa\.instalando-<versão>`, renomeia no fim e só então troca o ponteiro `programa\versao-atual.txt`; guarda as duas últimas versões; grava `<raiz>\iclass-instalacao.json` e o `iclass-pastas.json` da versão, com caminhos relativos para as pastas dentro da raiz), `--trazer-de` (cópia da pasta antiga para `<raiz>\.iclass-trazendo`, conferida e com o banco aberto antes de ir para o lugar; a pasta antiga só é lida), `voltarVersao` (backup de agora com a `backup-cli` da versão atual, restauração do `pre-atualizacao` com a `backup-cli` da anterior quando a atualização aplicou migrações, troca do ponteiro), `ligarComWindows` (atalho `IClass.lnk` no Inicializar, criado pelo `WScript.Shell`) e `desinstalar` (os dados só saem com APAGAR). Os modelos do Windows ficam em `scripts/release/modelos/`: `Instalar IClass.cmd` chama o `instalar.ps1` (pasta, dados antigos, regras do firewall por versão com elevação, atalhos, registro em `HKCU\...\Uninstall\IClass`) e o `desinstalar.ps1` (atalhos, regras do firewall, registro e programa); os dois `.ps1` são UTF-8 com BOM e toda a lógica de arquivos passa pelo `launcher.js`.

**Computador acordado durante a prova** (D13 do P6): `backend/utils/keepAwake.js` (`createKeepAwake`, com spawn e relógio injetáveis). O `server.js` chama `keepAwake.sync(db.memory)` no fim de cada volta do timer `exam-deadline-sweep` (10 s, e na primeira varredura do boot) e `keepAwake.stop()` no desligamento ordenado; na saída do processo, o PowerShell é encerrado na hora. No Windows, com aplicação em sala de espera, em andamento ou pausada, abre um PowerShell oculto que chama `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` e fica lendo a entrada; fechar a entrada (ou a queda do servidor, que fecha o pipe) devolve o estado. Não mexe no plano de energia. O status de controle diz `computadorAcordado`.

O `db.health()` e o `db.ping()` (`database.js`, H3b) dão o estado da gravação e do banco para o `/api/health` e o cartão Saúde do servidor (`routes/systemHealth.js`).

### Entrega do app na rede da sala (cache e compressão)

- **`/assets`**: os nomes têm o hash do conteúdo (`index-<hash>.js`), então ficam no aparelho para sempre (`public, max-age=31536000, immutable`). O build grava ao lado de cada arquivo de texto de 1 KB ou mais a versão `.gz` (gzip 9) e a `.br` (brotli 11) (`web/scripts/compress-assets.mjs`, no `npm run build`). O servidor manda a `.br` quando o navegador aceita br (só em HTTPS), senão a `.gz`, senão o original. Build antigo sem as versões comprimidas continua funcionando (original com cache imutável).
- **API e `index.html`**: sempre `no-store`. A recarga automática depois de uma atualização (cabeçalho `X-IClass-Build`) e o `index.html`, que aponta para os arquivos do build atual, dependem disso.
- **Respostas de texto da API** (JSON, `data.js`, apostilas `.md`, CSV) acima de 1 KB: gzip na hora, no pool de threads, quando o navegador aceita (`utils/httpCompression.js`). Fica de fora: HEAD, 204/304, `Cache-Control: no-transform`, resposta que já tem `Content-Encoding`, arquivos (`sendFile`), streams e ZIP. Enquanto o gzip roda, a resposta guarda o status e os cabeçalhos do envio: se a rota responde e depois lança, o que o `errorHandler` muda (tirar o `Content-Disposition`, pôr o 500) não alcança a resposta, que sai igual à de sem compressão.
- Sem pacote npm novo: só `zlib` do Node.

### utils/ — regras isoladas

Cada arquivo encapsula uma responsabilidade testável: `backup.js`, `examApplications.js`, `examAttempts.js`, `examGrading.js`, `examToken.js`, `security.js`, `safePath.js`, `rateLimit.js`, `uploadSecurity.js`, `authSessions.js` (único módulo de sessão: cria, procura pelo hash do token, confere, revoga, limpa as vencidas, marca a presença e calcula as linhas da tabela `auth_sessions`; fora dele ninguém lê nem grava `db.memory.sessions` ou `adminSessions`), `studentSessions.js`, `students.js`, `branding.js`, `buildIntegrity.js`, `parser.js`, entre outros. Novas regras de negócio devem nascer aqui, não dentro do handler da rota.

Fundação da fase 3 (C0b), pontos únicos que os grupos estendem sem mexer nos arquivos de hoje:

- **Hora da escola** (`utils/schoolTime.js`): `deadlineFromLocal(data, hora, fuso)` (prazo digitado no relógio da escola vira instante em ms; horário de verão pela regra do Temporal: hora que não existe vale depois do pulo, a que se repete vale a primeira), `schoolDateOf(ms)` e `localParts(ms)` no fuso de `settings.timezone`. Tarefas, agenda de prova e de material, dias não letivos e diário não criam outra conta de fuso.
- **Sino, calendário e fila** (`utils/studentFeeds.js`): `registerStudentNotificationProvider`, `registerStudentCalendarProvider` e `registerInstructorQueueProvider`. `GET /api/student/notifications`, `GET /api/student/calendar-events` e `dashboardAggregates.computeQueue` juntam os itens dos provedores depois dos de hoje (na fila e no sino do instrutor, cada item do provedor só para quem tem a permissão dele, `permissao`); provedor que falha fica de fora com o erro no `crash.log`.
- **Ciclo de vida dos dados do aluno** (`utils/studentDataHandlers.js`): toda coleção nova com aluno registra `registerStudentDataHandler({ collection, label, rename, anonymize, purge, merge, relink, count, exportSection })` no próprio módulo; a troca de e-mail (`renameStudentEmailEverywhere`), o anonimizar e o apagar de vez (`studentLifecycle.js`), as contagens de Cadastros encerrados, Meus dados (`studentDataExport.js`), a mesclagem e o religar depois de restaurar percorrem a lista depois dos blocos de hoje. No anonimizar e no apagar, os handlers rodam antes da pasta ir para a lixeira e, se um falha, a memória volta ao que era e o pedido é recusado (500 `student_data_handler_failed`); o handler deixa mover arquivo para o fim: devolve a função (ou `{ accepted, afterSave }`, com `accepted()` na hora em que todos deram certo) que roda depois do COMMIT; se a gravação falha, ela roda logo depois do COMMIT da regravação em segundo plano (`db.afterNextCommit`, do `dbWriter`), uma vez. ## 3. Persistência — o padrão `db.memory` + `db.save()`

O SQLite é usado como **key-value** (tabelas no formato `NOME (key TEXT PRIMARY KEY, value TEXT)`). O estado vive espelhado em memória em `db.memory` (um objeto com uma coleção por chave) e é serializado para o disco em `db.save()`.

```js
const db = require('../database.js');

db.memory.students.push(novoAluno);   // mutação em memória
await db.save();                       // persiste no SQLite
```

- `db.memory` é o objeto de estado (ver [MODELO_DADOS.md](./MODELO_DADOS.md)).
- `db.save()` (alias de `saveToDisk`) entra na fila do motor de gravação (`utils/dbWriter.js`): uma transação por vez, só com as linhas que mudaram, e resolve depois do `COMMIT`. Dentro de um pedido, a resposta espera as gravações dele (`utils/persistenceContext.js`); falha de gravação vira 503 `retryable`. Detalhes em [MODELO_DADOS.md](./MODELO_DADOS.md) e [PADROES_CODIGO.md](./PADROES_CODIGO.md).
- Sempre **mute e depois salve**; nunca escreva SQL cru fora de `database.js`.

- **Telas sob demanda** (`lib/lazyPage.js`): o `App.jsx` carrega cada tela e cada layout (painel do instrutor, portal do aluno, prova) com `lazyPage(() => import(...))`; só o login fica no pacote inicial. Cada tela vira um arquivo do build e o celular do aluno não baixa o painel do instrutor. Os ícones (`lucide-react`) ficam num arquivo só (`manualChunks` em `vite.config.js`), sempre importados pelo nome (`StatCard` usa o mapa `STAT_CARD_ICONS`). Em volta de cada `<Outlet />` dos layouts há um `<Suspense fallback={<PageLoading />}>`, na ordem área de erro → Suspense → portões → `StudentCourseGate`/`AdminCourseGate` → `<Outlet />`: o "Carregando..." aparece dentro do layout, com o menu à vista. Quando o arquivo de uma tela não chega, a falha nunca fica guardada pelo `React.lazy` (que guardaria o erro para toda visita seguinte): no lugar da tela entra uma tela de espera (`RecoveringPage`) que, cada vez que abre, confere se o servidor entrega a página (HEAD no endereço atual, sem cache, com `X-IClass-Background: 1` e prazo de 10 s por conferência, para o prazo de 3 minutos valer também com o servidor travado). Fora do ar (Reiniciar, queda, build sendo refeito) ou sem rede, fica no "Carregando..." e confere de novo (1 s, 2 s, 3 s e depois a cada 5 s, por até 3 minutos), sem recarregar, porque a recarga cairia na página de erro do navegador; quando ele volta, busca o arquivo outra vez e a tela abre. Se o servidor responde e o arquivo continua faltando (atualização que apagou o build anterior, ou o Chrome, que guarda a falha do import na mesma página), a página recarrega uma vez (marca de 30 s no sessionStorage, sem laço). Quem sai da tela para a espera, sem recarga; ao voltar, a espera recomeça. Passado o prazo, ou com a recarga recente, aparece a tela de erro do app. A espera é curta e com fim, encadeada por `setTimeout`, e não uma consulta periódica (`usePolling`). O portal do aluno busca o arquivo da prova 2 s depois de abrir. Toda tela nova entra no `App.jsx` com `lazyPage`. O `npm run check:bundle` (`web/scripts/check-bundle-size.mjs`) falha com o JavaScript da primeira abertura acima de 130 KB em gzip, com um `.js` acima de 350 KB, com `import * as` de `lucide-react` ou com um arquivo de `web/dist/assets` cujo nome o servidor não entrega.
- **Busca, confirmação e impressão** (fase 3, C0a): buscar e ordenar texto só com `lib/textSearch.js` (`normalizeSearch`, `matchesSearch`, `compareText` pelo `Intl.Collator('pt-BR', { sensitivity: 'base', numeric: true })`, `compareOrdinal` para chaves e datas ISO), igual ao `backend/utils/textSearch.js` do servidor; a tabela padrão (`components/ui/Table.jsx`) usa os dois. Confirmação pelo `components/ui/ConfirmDialog.jsx` (`title`, `message`, `confirmLabel`, `tone`, `requireReason`/`askReason`, `onConfirm` assíncrona; campos a mais vão como `children`, com `confirmDisabled` enquanto não valem), nunca `window.confirm`, `prompt` ou `alert`. Documento impresso pelo `lib/printDocument.js` (cabeçalho da escola, rodapé "Gerado por <nome da instituição> em <data>", `@page` A4, texto escapado). As guardas em `test/backend/contrato-telas.test.js` recusam `.toLowerCase().includes(`, `localeCompare` sem `'pt-BR'` em `web/src/features`, caixa nova do navegador e, onde há o histórico do git, caixa que ficou numa tela mudada desde 281029f (`NATIVE_DIALOGS_LEFT` só diminui). Mudança que o professor ou o aluno nota entra no `CHANGELOG.md`, seção "Não publicado".
- **Cliente único de API** (`lib/api.js`): nenhuma tela usa `fetch` cru. Repository pattern — tudo passa por `api.get/post/put/delete`. Cada pedido tem prazo (fase 2, H2-C e H9c): 60 s para o instrutor (pedido com a sessão do painel e o login dele), nenhum para o aluno (a prova tem as próprias tentativas), 10 s para as consultas periódicas e o envio da digitação, 15 s para o salvamento automático da prova (constantes em `lib/requestTimeouts.js`); as operações longas do professor (backup, restauração, compactar, limpar estado de prova, resetar, clonar, apagar e restaurar curso) vão com `timeoutMs: 0`, e os caminhos delas também ficam sem prazo quando a tela não diz nada. Prazo estourado ou sem rede: erro com `status: 0`, `err.timeout` ou `err.network` e mensagem fixa em português ("O servidor do IClass demorou demais para responder..." e "Sem conexão com o servidor do IClass..."). `background: true` manda `X-IClass-Background: 1` (o servidor não conta como uso da sessão); `signal` é o cancelamento de quem chama. O pedido com `keepalive` (saída da página) nunca tem prazo. Envio de arquivo (corpo `FormData`: restauração de backup, Biblioteca, comprovante da chamada, imagem do editor) vai pelo mesmo `api.post`, sem `Content-Type` JSON e sem prazo quando a tela não diz nada; o download do backup usa o `downloadFile`. Só a conferência do servidor do `lazyPage` (HEAD com prazo próprio) fica fora do cliente; o teste em `lib/api.test.js` falha com um `fetch(` novo em outra tela.
- **Consultas periódicas** (`hooks/usePolling.js`): toda tela que pergunta ao servidor de tempos em tempos (sino de notificações, fórum, dúvidas, provas do aluno, espera da matrícula, respostas do aluno no painel, configurações públicas e revalidação da sessão no `AuthProvider`, presença do aluno a cada 15 s e o `pollMs` do `useApi`) usa o `usePolling`, e não `setInterval`: uma consulta por vez, a próxima agendada só depois da resposta, recuo na falha (o dobro a cada falha, até 15 s ou o próprio intervalo, com variação de 0,8 a 1,2), nada com a aba oculta e consulta na hora quando ela volta, `runNow()` para consultar depois de uma ação, `resetKey` para recomeçar quando muda o que a consulta pergunta (o sino consulta a turma nova na hora; fórum e dúvidas descartam a resposta atrasada do curso anterior), prazo de 10 s e `X-IClass-Background: 1`. Exceções: a sincronização da prova (4 s) e o envio da digitação (2 s, lotes de até 500 teclas) não pausam com a aba oculta e têm a própria guarda de uma por vez no `ExamRunner`; o envio da digitação pedido durante outro sai logo depois dele, mesmo com a prova já fora da tela (Sair, desmontagem: o resto sai na hora), e a falha de rede espera o recuo (2 s dobrando até 30 s, com variação) em vez de reenviar a cada tecla; lote recusado pelo conteúdo (400, 413) ou de aplicação que não existe mais (404) é descartado, e com a sessão ou a turma recusadas (401, 403) as teclas ficam guardadas sem reenvio até uma sincronização aceita (fora da tela, descartadas); o Monitor (H2-D) consulta a situação dos alunos e as contestações a cada 3 s e a digitação ao vivo a cada 2 s pelo `usePolling`, a digitação com o cursor do servidor (`after`), só com as teclas novas. O teste `hooks/pollingSources.test.js` falha com um `setInterval` novo que não seja relógio da tela.
- **Erro de tela** (`components/ui/ErrorScreen.jsx`, fase 2, H9c): cada layout tem a área de erro (`AppErrorBoundary`) em volta do `<Outlet />`, dentro do `div` com `key={pathname}`: um erro numa página troca só a página pela tela de erro, com o menu à vista (texto próprio do painel e do portal, prop `description`), e trocar de página pelo menu volta ao normal. A raiz (`RouteErrorScreen`) continua pegando o erro fora dos layouts, e a prova continua com a `ExamErrorScreen`. A área de erro com `area` (`admin`, `aluno`, `prova`) e a raiz (`raiz`) mandam um aviso para `POST /api/client-error` (`lib/clientErrors.js`: mensagem sem endereços, caminho da página e versão do build; um envio por mensagem e no máximo cinco por carga da página), que vira a linha "erro de tela" no `crash.log` da pasta de dados. Cada campo do aviso vira uma linha só, e no `crash.log` só o cabeçalho de um bloco começa com "[" (linha de mensagem ou stack que comece assim é recuada): o texto mandado pelo navegador não forja um registro de outro usuário.
- **Providers de contexto** injetam auth, tema, toasts e branding. Ex.: `AuthProvider` injeta as credenciais no `api.js` via `setAuthProvider`.
- **features/** contém as telas; **components/ui/** contém os primitivos. Telas compõem primitivos, não os reinventam.

## 5. O problema dos arquivos monolíticos (resolvido)

A interface anterior concentrava lógica em poucos arquivos gigantes. A V3 quebra isso em: primitivos de UI reutilizáveis, uma tela por arquivo em `features/`, contextos para estado transversal e um cliente de API único. Ao adicionar telas, mantenha esse particionamento.

## 6. Decisões-chave (e o porquê)

- **SQLite key-value + memória**: simplicidade local-first; backup e restore viram serialização de JSON (ver `utils/backup.js`).
- **Server-authoritative**: segurança em rede local não pode depender do cliente. Gabarito e correção nunca saem do servidor.
- **Um router por área**: evita o retorno dos monólitos e facilita RBAC granular em `/api/admin`.
- **Paths configuráveis por env** (`ICLASS_DATA_DIR`, `ICLASS_CONTENT_DIR`, `ICLASS_ARCHIVE_DIR`): permite testes isolados em diretórios temporários.

Ver decisões de dado em [MODELO_DADOS.md](./MODELO_DADOS.md) e de segurança em [SEGURANCA.md](./SEGURANCA.md).
